Recipes

These are complete, runnable job files — not single-line snippets. Each one shows ops doing something that is awkward in a module-based tool: mixing command, shell, script, and upload tasks in one file, running the same job locally and remotely, or driving Linux and Windows hosts from the same YAML. Drop a recipe into jobs.yaml, point servers at your own, and run.

Not a module index. If you want df -h, run ops run jobs.yaml with a one-line command. These recipes exist to show compound jobs — the thing a configuration manager makes you split into roles, handlers, and templates.

App deploy with a health gate

Download a release, run a deploy script uploaded from disk, then block on an HTTP health check before the job is considered successful. One file, three task types, two servers in parallel.

jobs.yaml
---
description: deploy app and gate on health
servers: [web1, web2]
defaults:
  interpreter: bash
vars:
  app_version: "1.24"
  health_url: http://localhost:8080/health
env:
  APP_ENV: production
tasks:
  - name: download release
    command: curl -fsSL -o /tmp/app.tar.gz https://releases.example.com/app-{{ .app_version }}.tar.gz
    timeout: 2m

  - name: run deploy script
    script: ./scripts/deploy.sh
    env:
      APP_VERSION: "{{ .app_version }}"
      RELEASE_ID: "42"
    timeout: 5m

  - name: health check
    shell: |
      for i in {1..10}; do
        curl -f {{ .health_url }} && exit 0
        sleep 2
      done
      echo "health check failed after 10 tries" >&2
      exit 1
    timeout: 1m

Database backup with verification

Three steps: make the backup, prove it is non-empty, then raise an alert only if verification failed. The last task uses ignore_errors so the job completes and surfaces the alert message rather than aborting mid-run.

jobs.yaml
---
description: backup, verify, and alert
servers: [db1]
defaults:
  interpreter: bash
env:
  PGHOST: localhost
  PGUSER: admin
tasks:
  - name: create backup directory
    command: mkdir -p /backups/$(date +%Y%m%d)

  - name: dump database
    shell: |
      pg_dump app > /backups/$(date +%Y%m%d)/app.sql
    timeout: 5m

  - name: verify backup is non-empty
    command: test -s /backups/$(date +%Y%m%d)/app.sql

  - name: alert on missing backup
    shell: |
      echo "backup verification failed for $(date +%Y%m%d)" | mail -s "backup failed" ops@example.com
    ignore_errors: true

Config render + upload + reload

Upload a templated config from a local file, patch a value with an env-backed sed, validate the syntax, and reload the service. The upload task carries a file you keep in version control; the shell task does what a templating engine would, but in plain shell you can read.

jobs.yaml
---
description: render, validate, and reload nginx
servers: [web1, web2]
defaults:
  interpreter: bash
vars:
  domain: example.com
tasks:
  - name: upload base config
    upload: ./configs/nginx.conf
    dest: /etc/nginx/nginx.conf

  - name: set server name
    command: sed -i "s|DOMAIN|$DOMAIN|" /etc/nginx/nginx.conf
    env:
      DOMAIN: "{{ .domain }}"

  - name: validate config
    command: nginx -t

  - name: reload
    command: systemctl reload nginx

Same script, local and remote

A single job file runs unchanged against remote servers or the local machine. Develop and test against --local, then point the same file at real hosts. No inventory change, no role rewrite.

jobs.yaml
---
description: clean up old logs
servers: [web1, web2]
defaults:
  interpreter: bash
env:
  LOG_DIR: /var/log/app
  KEEP_DAYS: "7"
tasks:
  - name: run cleanup script
    script: ./scripts/cleanup.sh
    timeout: 5m
terminal
$ ops run jobs.yaml --local          # test on this machine
$ ops run jobs.yaml                    # run on web1, web2
$ ops run jobs.yaml --dry-run          # show what would run

Linux and Windows in one job

Per-task servers and interpreter let one file target heterogeneous hosts. The Linux task runs bash; the Windows task runs powershell against a uploaded script — same job, same fan-out, same summary.

jobs.yaml
---
description: cross-platform health check
servers: [linux1, win1]
tasks:
  - name: linux disk and memory
    command: |
      echo "== disk ==" && df -h /
      echo "== memory ==" && free -m
    interpreter: bash
    servers: [linux1]

  - name: windows disk check
    script: ./scripts/check-disk.ps1
    interpreter: powershell
    env:
      THRESHOLD_GB: "10"
    timeout: 2m
    servers: [win1]

Rolling restart with batches

Run a job against a subset of servers with -S, verify, then move to the next batch. No built-in batch primitive — you drive it from the CLI, which means it works in a shell loop, a CI pipeline, or behind xargs exactly the way you would expect.

jobs.yaml
---
description: rolling restart
servers: [web1, web2, web3, web4]
defaults:
  interpreter: bash
tasks:
  - name: drain
    command: /usr/local/bin/drain.sh
    timeout: 1m

  - name: restart
    command: systemctl restart app

  - name: warm up
    shell: |
      for i in {1..5}; do
        curl -f http://localhost:8080/health && exit 0
        sleep 2
      done
      exit 1
    timeout: 30s
terminal
$ ops run jobs.yaml -S web1,web2 && ops run jobs.yaml -S web3,web4
$ ops plan jobs.yaml -S web1,web2     # dry-run the batch first

Safe to run twice

ops does not track desired state — and that is the point. Idempotency is a property of the shell you write, expressed with the guards you already know: test -f, grep -q, test -s. These are the same checks a Makefile uses. They read top-to-bottom, they fail loudly when wrong, and they survive a second run because the guard short-circuits the work.

jobs.yaml
---
description: install once, configure once
servers: [web1, web2]
defaults:
  interpreter: bash
vars:
  domain: example.com
tasks:
  - name: install nginx if missing
    command: command -v nginx >/dev/null || apt-get install -y nginx

  - name: write config if absent
    command: test -f /etc/nginx/conf.d/app.conf || cp /tmp/app.conf /etc/nginx/conf.d/app.conf

  - name: set domain only when it differs
    shell: |
      grep -q "{{ .domain }}" /etc/nginx/conf.d/app.conf && exit 0
      sed -i "s|server_name .*|server_name {{ .domain }};|" /etc/nginx/conf.d/app.conf
      systemctl reload nginx

  - name: backup only if today's dump is missing
    shell: |
      dest="/backups/$(date +%Y%m%d)/app.sql"
      test -s "$dest" && exit 0
      mkdir -p "$(dirname "$dest")"
      pg_dump app > "$dest"

The pattern is the same in every case: check the thing that proves the work is already done, skip if it does, do the work if it doesn't. No module, no state store, no changed vs ok — just a guard and a command, which is exactly what a declarative module compiles down to internally.

Why not a creates: field? A Makefile-style skip-if-path-exists guard would cover the easy cases, but it would only ever be a partial answer, and the moment the runner has one piece of state it is expected to grow the rest. Keeping idempotency in shell means the guard is visible, editable, and works the same way locally and remotely — which is the whole bet.
